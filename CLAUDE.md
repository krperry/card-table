# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Snapshot

Browser-based multiplayer card game platform built on Node.js + Express + Socket.IO (package name `socket-uno`, but the first game is branded **Lumo** — a UNO-like game with house rules; see `public/lumo-rules.md`). **Hearts** is the second fully implemented game, and **Spades** is the third. The platform also registers Cribbage as a non-playable placeholder, with room to add more (`plan_card_game.md`, `README.md`). Accessibility (keyboard, screen-reader, mouse/touch) is a first-class requirement for every game, not an afterthought.

Runtime entrypoints:
- `server.js` — shared Socket.IO server: accounts/auth, lobby/table create/join/leave/kick, disconnect-grace/reconnect, and the generic per-game dispatchers (`buildTableState`, the `startGame` handler, `removePlayerFromTable`, `reclaimSeatAfterReconnect`, the test-only `__testSetTableState`). Delegates all game-specific rules/state to whichever module in `games/` matches a table's `gameType` — see "Game modules" below. The client never re-implements game rules; server logic is authoritative for every game.
- `games/registry.js` — assembles `GAME_MODULES`/`GAME_DEFINITIONS` from each game's factory function; called once from `server.js` at startup with a small `deps` object of shared primitives (`io`, `tables`, `shuffle`, `emitTableState`, `addComputerPlayersToTable`, ...).
- `games/lumo/index.js` — all Lumo/UNO rules, deck, turn/stacking/Give-Plus-One logic, and bot AI (moved out of `server.js`; see `public/lumo-rules.md` for the house rules).
- `games/hearts/index.js` — Hearts state/socket handlers, wired on top of `games/hearts/rules.js` (a pure, side-effect-free rules engine — deck/deal/legal-plays/trick-resolution/scoring/shoot-the-moon, directly unit-tested in `tests/hearts-rules.test.js` with no server spawn) and `games/hearts/bots.js` (simple legal-card/pass-card heuristics).
- `games/spades/index.js` — Spades state/socket handlers, wired on top of `games/spades/rules.js` (a pure, side-effect-free rules engine — deck/deal/legal-plays/trump-aware trick-resolution/turn-sequenced bidding/partnership scoring, directly unit-tested in `tests/spades-rules.test.js` with no server spawn) and `games/spades/bots.js` (simple legal-card/bid heuristics). See the "Game modules" section below for the fixed-partnership design this game introduces.
- `public/index.html` — login / game-picker / lobby / table / game screens, all in one page, toggled via CSS `hidden` class. `#game-panel` (Lumo, canvas-based), `#hearts-panel` (Hearts, native-button-based), and `#spades-panel` (Spades, native-button-based) are sibling panels inside `#table-view`, shown/hidden by `gameType`.
- `public/main.js` — the **shared** client shell: screens, lobby, auth, table lifecycle, ARIA live-region speech (`srSpeak`), overlay open/close scaffolding, touch-helper wiring, DOM cache (`el`), and `appState`. Does not contain Lumo-, Hearts-, or Spades-specific rule/rendering logic.
- `public/games/lumo/lumo-client.js` — Lumo's canvas rendering, card model, keyboard shortcuts (`handleGameKeys`), color picker, stacking/Give-Plus-One UI, rules overlay, and all Lumo-only `socket.on(...)` handlers.
- `public/games/hearts/hearts-client.js` — Hearts' hand/passing/trick UI (native `<button>` elements, not canvas — see its header comment for why), keyboard shortcuts, and all Hearts-only `socket.on(...)` handlers.
- `public/games/spades/spades-client.js` — Spades' bidding/hand/trick UI (native `<button>` elements, same reasoning as Hearts), keyboard shortcuts (including partner/bids announcements, the one new accessibility need a partnership game introduces), and all Spades-only `socket.on(...)` handlers.
- `public/images/lumo/cards/` — Lumo's own custom card art (color+rank/action SVGs). `public/images/playing-cards/` — standard 52-card deck art (`<RANK><SUIT>.svg`, e.g. `QS.svg` = Queen of Spades) used by Hearts and Spades today, kept generic for future standard-deck games.
- `public/style.css` — layout and visual styling (shared + per-game classes, e.g. `.hearts-*`, `.spades-*`).
- `public/uno-speech.js`, `public/touch-helpers.js` — small standalone helper modules (UMD-style, usable from both browser and `node:test`) for screen-reader speech text and touch/click de-duplication respectively. Exported as `CardTableUnoSpeech` / `CardTableTouch` on `window` when loaded in-browser. `uno-speech.js` is Lumo-specific (the "say Lumo when down to one card" call-out) despite living outside `games/lumo/`.
- `public/control.js` — legacy standalone pointer/keyboard helper; not wired into the main client flow unless you check first.

**No bundler**: the client is plain `<script>` tags (see `index.html`'s script order: `main.js`, then each game's `*-client.js`, then a final `init();` call). All scripts share one global scope, the same way multiple classic `<script>` tags in a browser always do — a game-client file can reference `appState`/`el`/`socket`/`srSpeak`/etc. defined in `main.js` directly, with no import/export or dependency-injection needed. Game-client files must not call anything at their own top level that depends on another not-yet-loaded script; put such logic inside a function so it only runs after `init()`.

Server state (accounts aside) is in-memory only: lobby tables and active games reset on server restart. Player accounts persist to `data/accounts.json` (runtime data, not a source of truth for code changes). Server errors/warnings are also appended to `logs/server.log` (`writeLogLine`/`logServerError`/`logSocketWarning`).

## Commands

```
npm install    # install dependencies
npm start      # start the server (node server.js)
npm run stop   # kill whatever process is listening on the server's port (Windows: netstat+taskkill, else lsof+kill)
```

The server listens on `process.env.PORT || 4123` (`server.js`). There is no lint or build step.

### Tests

Tests use Node's built-in `node:test` runner (no Jest/Mocha). Most test files spawn a real `server.js` child process via `child_process.spawn` with its own `PORT` env var and drive it with `socket.io-client` over a real socket connection — so they are not simple unit tests and must not run with overlapping ports. Pick an unused port when adding a new integration test file (existing files use values in the 3100s–3170s range — grep `tests/*.test.js` for `PORT:`/`port =` before picking one). `tests/hearts-rules.test.js` and `tests/spades-rules.test.js` are the exceptions: they test `games/hearts/rules.js`/`games/spades/rules.js` directly (pure functions, no server, no port) and are the fastest place to add new Hearts/Spades rule coverage.

On Node 25+, `node --test tests/` (directory form) does not discover files the same way it used to — use an explicit glob instead:

```
node --test tests/*.test.js                  # run all tests
node --test tests/hearts-rules.test.js       # run a single test file
```

`DISCONNECT_GRACE_MS` and `BOT_MOVE_DELAY_MS` are read from the environment and can be shortened in tests that exercise reconnection or bot pacing (see existing test files for the pattern).

The repo root has some `debug-start*.js`-style manual one-off debugging scripts — not part of the automated test suite (none currently checked in, but treat any as such if you find them).

## Architecture

### Shared server (`server.js`)

All state lives in module-level objects:
- `accounts` — loaded from/saved to `data/accounts.json`; passwords stored as PBKDF2 salt+hash (`hashPassword`/`verifyPassword`), never plaintext. Remember-me uses a separate hashed token (`issueRememberToken`/`hashRememberToken`), not the password hash — see the Security Decision in `plan_card_game.md` (never treat a password hash as a remember-me secret).
- `tables` — keyed by table id, holds lobby + in-progress game state. `table.game` is entirely owned/shaped by that table's game module (Lumo and Hearts use very different shapes there).
- `GAME_DEFINITIONS`/`GAME_MODULES` — built by `games/registry.js` at startup (`type`, `name`, `playable`, `minPlayers`, `maxPlayers` per game, plus the module's full interface). `createTable`/`joinTable` gate on `gameDefinition.playable`/`maxPlayers`; don't hardcode a player-count constant when touching that code, read it from the definition.

Socket.IO handlers are registered in `onConnection` (bottom of the file):
- **Auth**: `resumeLogin`, `registerAccount`, `login`, `logout`, `deleteAccount`.
- **Lobby/table**: `requestLobbySnapshot`, `createTable`, `joinTable`, `leaveTable`, `kickPlayer`, `startGame` (delegates to `GAME_MODULES[table.gameType].startGame(table)`). `buildLobbySnapshot`/`emitLobbySnapshotAll` push table lists to all connected sockets.
- **Gameplay**: each game module's `registerSocketHandlers(socket)` is called for every connected socket (Lumo: `playCard`/`drawCard`/`acceptStackPenalty`/`submitGiveCard`/`requestDiscardCard`/`ackRoundSummary`; Hearts: `heartsPlayCard`/`heartsSelectPassCards`/`heartsAckTrick`/`heartsAckHandSummary`; Spades: `spadesPlaceBid`/`spadesPlayCard`/`spadesAckTrick`/`spadesAckHandSummary`). Event names are namespaced per game (Hearts events all start with `hearts`, Spades events all start with `spades`) specifically so a table running one game can never be affected by another game's events — don't reuse a name across games.
- **Reconnection**: on disconnect, `scheduleDisconnectGrace` holds the player's seat open for `DISCONNECT_GRACE_MS` (default 45s) before the seat is actually removed; `reclaimSeatAfterReconnect` restores the seat if the same account reconnects in time, then calls the table's game module's `onReconnect(table, player, previousSocketId)` hook to resync any in-flight state (hand, current turn, pending acks, ...). Relevant when debugging "player vanished from table" reports — check whether it's still inside the grace window.

`buildTableState(table, socketId)` is the single generic per-socket state shaper — it merges the game-agnostic table fields with whatever `GAME_MODULES[table.gameType].buildTableStateExtra(table, socketId)` and `.getPlayerSummaryFields(table, player)` contribute (Lumo: `stackState`/`givePendingState`/`cardCount`/`score`; Hearts: a nested `hearts: {...}` object plus `cardCount`/`score`; Spades: a nested `spades: {...}` object plus `cardCount`/`score`, where `score` is a *team* total shared by both partners — see the Spades section below). Follow this pattern when adding new per-game client-visible state rather than broadcasting raw table objects or hardcoding a new field into `buildTableState` itself.

### Game modules (`games/`)

Each playable game is a **factory function**: `module.exports = function createXGame(deps) { ...; return { type, name, minPlayers, maxPlayers, normalizeMatchSettings, getMatchSettings, initializeGameState, startGame, buildTableStateExtra, getPlayerSummaryFields, onPlayerRemoved, onPlayerCountSettled, onReconnect, applyTestState, registerSocketHandlers, ... }; }`. `deps` (passed once by `games/registry.js`) is a small set of shared primitives the module needs back — `io`, `tables`, `shuffle`, `getPlayerIndex`, `normalizeIndex`, `clampInteger`, `emitTableState`, `emitLobbySnapshotAll`, `addComputerPlayersToTable`, `findTableBySocket`. This is dependency injection, not a plugin framework — most of a module's code is ordinary functions closed over those `deps`.

**`games/lumo/index.js`**: `createDeck`/`shuffle`/`cardColor`/`cardType`/`cardScore`/`canPlayCardOnBoard`/`hasPlayableCard`/`getCurrentBoardColor`/`advanceTurn`/`getNextPlayerIndex`. Per-table match rules (`normalizeMatchSettings`/`getMatchSettings`) include configurable `allowDrawTwoStacking`/`allowWildDrawFourStacking` (draw-stacking and Wild Draw Four challenge flow are both implemented and host-configurable per table — don't assume they're absent). The "Give +1" mechanic (`isGivePlusOneCard`, `performSubmitGiveCard`) is a Lumo-specific house rule not present in standard UNO: see `public/lumo-rules.md` for exact rule text (e.g. a Give +1 can never be used to give away your last card) before changing its logic. Round/match flow: `beginRound` → `initializeGameState`/`drawStarterCards` → gameplay events → `endRound` (scoring via `calculateRoundPoints`; match target and round cap are host-configurable, default winning score 500 / max rounds 30). The module also re-exports `createDeck`/`cardColor`/`cardType`/`cardScore`/`describeCard`/`isGivePlusOneCard`, which `server.js` re-exports again at the bottom of the file for `tests/lumo-assets-and-deck.test.js`'s `require('./server.js')` usage — keep that passthrough in sync if you rename any of them.

**`games/hearts/`**: `rules.js` is intentionally pure (no `io`, no `table`, no randomness — `deal()` takes an already-shuffled 52-card array; shuffling happens in `index.js` via `deps.shuffle`) so the 24 rule requirements (deck/deal, follow-suit, Hearts-breaking incl. the only-Hearts-remaining exception, first-trick restrictions, scoring incl. shoot-the-moon, all four passing directions + Hold + sequence repeat, game-end/winner) are covered directly in `tests/hearts-rules.test.js` with zero server involvement. `index.js` wires that engine into `table.game` state and the `hearts*`-prefixed socket events; `bots.js` holds the (deliberately simple, no lookahead) bot heuristics. A card is a two-character string that is also its asset filename stem in `public/images/playing-cards/` (`"QS"` = Queen of Spades = `QS.svg`) — no translation layer needed between rules engine, wire payloads, and rendering. Trick/hand pacing reuses Lumo's `pendingRoundAcks` concept: after a trick resolves, the server waits for every human seat's `heartsAckTrick` (`table.game.pendingTrickAcks`) before dealing the next lead, and similarly `pendingHandAcks`/`heartsAckHandSummary` gate the next hand — bots never need to ack (only human socket ids are tracked in those maps). Hearts always seats exactly four players: `startGame` tops the table up to 4 with computer players (`addComputerPlayersToTable`) rather than requiring a minimum; because state (`hands`/`captures`/`turnIndex`) is keyed by a fixed 4-seat index, a human leaving mid-hand ends the hand/table rather than trying to hot-swap a bot into their seat (`onPlayerCountSettled`) — the disconnect-grace window (shared, unaffected by this) is what actually protects against a brief disconnect.

**`games/spades/`**: the one architectural concept Spades introduces that Hearts/Lumo don't have — it's a **fixed-partnership team game**, not every-player-for-themselves. `rules.js` follows the same pure/no-`io` shape as Hearts' rules engine, duplicating (not importing) the deck/sort/rank helpers per the project's per-game self-containment precedent, plus Spades-specific exports: `getLegalPlays` (no first-trick restriction, unlike Hearts, but spades cannot be led until "broken" — same only-suit-remaining exception as Hearts' Hearts-breaking rule), `resolveTrick` (spades are permanent trump — the highest spade played wins the trick regardless of what was led, the one place trick resolution genuinely differs from Hearts), `getLegalBids` (0-13, where 0 is Nil), `DEFAULT_TEAMS`/`getTeammateIndex` (seats 0 & 2 are one team, seats 1 & 3 are the other — fixed for the whole game, set once from seat order in `initializeGameState`), and `scoreHand` (partnership scoring: 10×bid + 1 per bag on a made contract, -10×bid on a failed one, ±100 Nil bonus/penalty, and a -100 bag penalty every time a team's running bag count reaches 10). `index.js` differs from `games/hearts/index.js` in two structural ways: (1) the dealer rotates one seat per hand instead of following a card-holder, and the seat left of the dealer both bids first and leads the first trick; (2) bidding is turn-sequenced (`performPlaceBid` validates whose turn it is, like trick play, and broadcasts `spadesBidState` after each bid) rather than Hearts' simultaneous-submit passing phase, since real Spades bidding strategy depends on hearing your partner's and opponents' bids first. Because `table.scores` is a generic per-player-name map `server.js` itself initializes (not game-module-owned), `finishHand` writes each team's hand-point total into **both partners' entries** under their own names, so the existing generic score plumbing (`getPlayerSummaryFields`, `buildTableState`) needs no changes to display a team's running total per player row. Hearts' seat-index-keyed-state reasoning for `onPlayerRemoved`/`onPlayerCountSettled` (a departed seat can't be hot-swapped mid-hand, so the hand/table ends; disconnect-grace is the real protection) applies identically here, extended to cover the fixed partnership too.

Adding a new game: create `games/<name>/index.js` following the factory shape above, register it in `games/registry.js`, add uniquely-`<name>`-prefixed socket event names, and give it non-playable-stub-style entries removed from `GAME_DEFINITIONS` (see how Hearts and Spades replaced their own stubs). Keep genuinely reusable pieces (e.g. `games/hearts/rules.js`'s standard-deck concepts) out of a Lumo-shaped abstraction — Lumo's card model is custom and shouldn't be forced to fit a standard-deck interface, per `plan_card_game.md`.

### Shared client (`public/main.js`)

Single-page state machine driven by `setScreen(screen)` toggling the panels defined in `index.html` (`auth-view`, `game-picker-view`, `placeholder-view`, `lobby-view`, `table-view`). `appState` holds client-side session/lobby/hand state (both generic fields and per-game fields — Hearts' and Spades' clients each add their own `appState.hearts*`/`appState.spades*` fields at load time via `Object.assign`); `el` is a cache of DOM element references built at module load. `render()` is the generic re-render entry point; `getActiveGameType()` resolves which game is currently active (seated table's `gameType`, falling back to `selectedGameType`) and drives a `gameType`-keyed dispatch at several branch points (which settings fieldset to show, which of `#game-panel`/`#hearts-panel`/`#spades-panel` to show, which rules doc `RULES_BY_GAME` loads, which help-content list `openHelpOverlay` shows) — `render()` then calls each game's own render function (`renderHeartsPanel()`, `renderSpadesPanel()`, or Lumo's canvas redraw path). Extend those branch points rather than duplicating `render()`'s auth/lobby/table-lifecycle logic per game.

Server logic is authoritative — the client renders and forwards intent, it does not re-implement game rules. When adding gameplay behavior, change the relevant `games/<name>/index.js` first and keep the client as a thin presenter.

Accessibility is a first-class concern, not an afterthought:
- ARIA live regions (`#sr-status`/`#sr-alert`) narrate turn/action/announcement events via the generic `srSpeak(text, priority, options)` in `main.js` — both game clients call it directly, don't build a parallel announcement mechanism.
- `public/uno-speech.js` builds Lumo's "say Lumo when down to one card" announcement text specifically (still called "Uno speech" internally).
- All game actions are reachable by keyboard as well as mouse/touch. Lumo: `handleGameKeys` on the canvas (arrow-key hand navigation, letter shortcuts — see `#help-content-lumo` in `index.html` for the full list). Hearts: `handleHeartsKeys` on `#hearts-panel`, plus roving-tabindex arrow-key navigation across card `<button>`s (`heartsBindCardGridKeys`) — see `#help-content-hearts`. Spades: `handleSpadesKeys` on `#spades-panel`, with the same roving-tabindex machinery copied/renamed `spades*` (`spadesBindCardGridKeys`) covering both the card-hand grid and a bid grid (Nil plus 1-13) — see `#help-content-spades`, which also documents Spades-only shortcuts for announcing bids-so-far and your partner's name (the one new accessibility need a partnership game introduces beyond what Hearts already solved). All three back onto `public/touch-helpers.js` for touch/click de-duplication via `bindPress`/`bindPressNoFocus`.
- The `?`/Escape help overlay (`#help-overlay`) is shared; it swaps between `#help-content-lumo`, `#help-content-hearts`, and `#help-content-spades` based on the active table's `gameType` (see `openHelpOverlay`) and must restore focus to the game board/panel on close.
- Hearts and Spades intentionally use native `<button>` elements (not canvas + hit-testing) for hand/passing/bidding/trick UI, per their module header comments — prefer that pattern for any future standard-deck game's UI too.

## Working Conventions

- Keep shared table/lobby/account/networking/accessibility logic in `server.js`/`public/main.js`; keep game-specific rules and rendering in that game's `games/<name>/` and `public/games/<name>/` module. Don't move gameplay rules into the browser.
- Preserve existing game flow and accessibility behavior (keyboard support + screen-reader announcements) when making changes, for every implemented game, not just the one you're touching.
- Most bugs cross the Socket.IO boundary between server and client — when changing lobby/gameplay behavior, verify both sides together (a `node --test` run plus a manual two-browser-session pass).
- New game types should follow the `games/registry.js` factory pattern and the existing placeholder pattern (`playable: false`, no `games/<name>/` module) until their rules are actually implemented server-side, per `plan_card_game.md`.
